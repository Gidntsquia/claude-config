you, in the round 9 planner session (fixture plans/PLAN.md, ## Ask)

Number 4 was next round's battles.

A little before 11:55 on Saturday morning the GPU was partway through generation 7 of that day's first plain run (r9pre-ab-default-1), and most of its workers had nothing to do. That generation took 12.84 s.

Across the run, 42.6% of the GPU's time was tail, the stretch after the quick workers run out of battles while the chip waits for the slowest one, so about 5.5 s of those 12.84 s were waiting.

Number 4 gives the idle workers something to do: each picks a team likely to survive the cut and fights its next-round battles early. The code calls this speculation, and the early battle goes into a memo if the team survives and into the bin if it is cut.

But the same generation with the fix on (r9pre-ab-tail-1) took 12.94 s. Three runs a side that morning, a warm generation (generation 4 onward, once the pool is full) went from 12.60 s to 13.63 s, n = 3.

The fix cost 1.03 s a generation. You asked for less waiting and the chip found a way to wait more.

⏱️ Where did the extra second land?

It landed in the tail, the one place it was supposed to leave. The morning runs had no profiler on, so this comes from the afternoon build of the same fix, where it was.

In the afternoon's plain run (r9-ab-default-1), generation 7 spent 6.58 s in the main battle kernel and 5.04 s in the tail. With the fix on (r9-ab-tail-1), the same generation spent 3.31 s in the kernel and 6.61 s in the tail.

The main battles shrank by about three seconds, because some had already been fought. The tail grew by a second and a half, and over the whole afternoon run its share went from 42.0% to 55.4%.

Why the tail grows is the one thing the files do not say. The log shows speculation stopping when the main battles end, so my guess is memo traffic and ranking work landing in the tail window, and the profiler's buckets are too coarse to confirm it.

🧮 How much work did the idle workers do?

A lot of it, and most of it for teams that were about to be cut. The run with the fix on that was paired with our generation 7 (r9pre-ab-tail-1) fought 65,127 battles early. The team behind 56% of them did not survive the cut, so those battles went in the bin. The next round got 21,928 battles from the memo, 12% of its pool of 182,630.

So the chip was busy where it used to sit, and more than half of that busy time went to battles nobody needed. The memo paid back one battle in eight and the bin took the rest.

🔭 Is it any better on a long run?

A long run makes it far worse. The one long run with the fix on (r9pre-full-tail) was taking 127.1 s a generation by generation 79 and died at 80 of 100 (exit 1). The plain 100-generation run did generation 79 in 10.9 s. A run that died is a hint and no more, and the hint is that the cost grows with the pool.

The 40-generation standard run with the fix, full-tail-1, is not run: it exited 1 at generation 14 of 40 when the sidecar lost the GPU lock. So a full standard run with the fix on is not measured, and the plan's ship test wants that number.

🔀 Why trust the morning over the afternoon?

Because the morning has three runs a side and the afternoon has one. That afternoon pair came out 12.12 s with the fix against 12.60 s without (n = 1), which looks faster, and I do not know what changed between the 11:53 fork and the 14:05 build. One run each decides nothing.

The files for that afternoon run also quarrel. The summary file runs.json has r9-ab-default-1 at 12.80 s with a tail share of 42.6%, which are the morning's numbers under the afternoon's name.

The lit fork's evidence-profile.json has the tail share at 35.2%, by a different ruler (time after half the main battles ended). That conflict stays on the table, because I have no reason to trust one file over the other.

🧪 Did the other shapes do any better?

None of them did enough to change the answer. The certain feed, which pushes battles for teams already proven to survive into the running kernel through a queue, came out at 13.20 s, 0.59 s slower than plain (n = 3).

Tail v2, the same speculation with the trigger at a quarter of the workers idle instead of half, came out at 9.10 s in its only run (n = 1). One run with nothing beside it leaves that number unproven, and it is also the only number in this study that points the way you wanted.

✅ Were the answers right?

They were right, and the five-generation checkpoints with the fix on matched the plain path, 5 of 5, and the 3v3 verify pass agreed with the CPU on 100.00% of winners. The fix lost time and nothing else.

🔁 Back to that generation

Generation 7 of the first plain run took 12.84 s with the wait in it and 12.94 s with the wait filled. The generation after it went from 17.47 s to 19.59 s. About 5.5 s of waiting was there to be won back, and none of it came back.

So the ask is built, it gets the right answers, and it is slower by 1.03 s a warm generation, with the long run saying the slope is the real problem, so it stays off and the plain path is as it was.

Compact state, the other change from this round (battle state kept on the chip instead of in slow memory), is its own −0.54 s and is unaffected.
