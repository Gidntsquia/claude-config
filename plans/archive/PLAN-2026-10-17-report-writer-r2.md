# Spec: report-writer agent that turns collected study data into a short, sourced, actionable report, with a fixture from the pogo GPU rounds 8–9

## Ask
"I want to make a new subagent called "report-writer." … The Claude session is excellent at collecting data, but it is poor at synthesizing the data into a report that I can actually glean information from and do something with. I want the data from those recent sessions to be turned into a fixture for tests on the new subagent to build reports from. Common issues: 1. Walls of AI text — elaborates on minuscule points, distracts from the important things, low time-to-gain. 2. Lack of focus — includes everything, valuable analysis lumped with unimportant, sections not related to each other. 3. Inaccuracies — two different values for idle tail time per generation; one wrong value means I must be skeptical of every value. 4. I like picture+words explanations and seeing actual data so I know the AI isn't making things up. Ideal: read a report and immediately know where we should go next, or mistakes we made that need correcting; detect quickly when the AI looked in the wrong place and course correct. Help me decide the criteria for a "good" report; this may take a few rounds."

Round 1 — Input: "Raw data dir + the question", "The spec (PLAN.md) and worker notes", "A previous report draft to rewrite", "The session transcript", "Only read session transcript and other things as necessary". First screen: "Verdict + one next action", "Mistakes and gaps up front", "One chart that shows the decision", "Decision table of all candidates", "Let's try these, though I need to see them first before I can truly judge if these are the correct criteria. This applies to these and all the future criteria. Further, the nature of the report should depend on the data and desired outcomes. The best report for this data may not be the best report for another situation". Accuracy: "One numbers table, quoted everywhere", "Every number carries its source", "Missing or conflicting = say so, never fill", "A gain needs a spread or it isn't a gain", "If we have too many unproven claims and thus can't make a verdict, then we should immediately send things back to the worker to collect more data until we can actually arrive at a verdict. The key is to do this without needing interaction from me. All I care about is the final report being good and actionable". Form: "Either a phone mode or a Desktop mode. In phone mode, phone sized PNGs only. For desktop mode, just an HTML report since that shows up best in my Firefox window".
Round 2 — Send-back: "Writes a data request, worker loops". Focus: "Every section names the verdict line it supports", "Unimportant data goes to a collapsed appendix", "No hard caps. I want the report builder to be flexible. They should be concise, but even a concise report on an especially important task or on a lot of data may be long". Tests: "Mechanical checks + rubric + your review rounds", "Fixture = GPU round 8+9 data plus the bad reports", "Planted traps in the fixture". Placement: "agents/report-writer.md in claude-config", "Opus, high effort", "Phone vs desktop chosen by a flag or by you", "The plan will call for the report to be written using the report writer skill. I'll tell the planner that's what I want. We may change the planner later to do this automatically, but not for now. The phone/desktop mode will be the same".

## What to build
A new agent file `agents/report-writer.md` (prose prompt like planner/worker/evaluator, Opus, high effort) that is given a data directory and the question the study was meant to decide, reads the spec, worker notes, any prior report draft and the session transcript only as needed, and produces one report whose first screen settles the verdict, the next action, the gaps and mistakes, with one decision chart and a decision table; every number in it comes from a single numbers table that names its source file and field; missing or conflicting data is said, never filled; a gain without a spread is "unproven"; and when the data cannot support a verdict it writes `plans/DATA_REQUEST.md` for the worker instead of guessing. The same content renders as a desktop HTML page or as phone-width PNG cards. Alongside it: a fixture built from the pogo GPU round 8–9 study data with planted traps, mechanical checks, a rubric file that grows from the user's review rounds, and a runner that produces the report for the user to read.

## Requirements
1. (user) `agents/report-writer.md` exists, frontmatter `model: opus`, `effort: high`, tools Read/Glob/Grep/Bash/Write/Edit, and is runnable as `claude --agent report-writer "<data dir> — <question> [phone|desktop]"`. README agent list and CHANGELOG `## Unreleased` mention it (default).
2. (user) Input: the prompt names a data directory and the question the study must decide. The agent also reads `plans/PLAN.md`, `plans/WORKER_NOTES.md`, any prior report in the data dir, and the collecting session's transcript, each only when the data dir leaves something unexplained (what a run was for, why it failed). Every figure in the report traces to a file in the data dir; nothing comes from the transcript or prior report alone.
3. (user) First screen (what fits in 390 px × ~800 px, or the top of the HTML page before any scrolling at 1530 px wide): verdict in one sentence; one next action; the one number that decided it with n, spread and source; a "Wrong or missing" box listing failed runs, unmeasured quantities and assumptions the data cannot back; one chart that shows the decision; a decision table with one row per candidate: name in plain words, measured change, spread, n, verdict (keep / drop / rerun / unproven).
4. (user) Numbers: the agent first writes `numbers.json` in the output dir: every figure it will use, with value, unit, run name, source file and field. Prose, tables and charts only quote `numbers.json`; a quantity has exactly one value in the whole report. Each figure in prose is followed by its run name or source in short form (e.g. "12.80 s (r9-ab-default-1)"), and the decision table and charts cite the file.
5. (user) A run with non-zero exit, no output, or absent file yields "not run" / "not measured", never a number or a direction word. Two sources disagreeing yield "conflict: A says X, B says Y" with both sources. A claimed gain shows n, mean and spread for both sides and is "unproven" if n<2 on either side or the difference is within either spread.
6. (user) Send-back: if the verdict cannot be reached (the deciding candidate is unproven, or the question's quantity is unmeasured), the agent writes `plans/DATA_REQUEST.md`: each missing measurement, why it blocks the verdict, the command if known from the data dir, and the loop count; it does not write the report. The worker prompt gains one paragraph: if `plans/DATA_REQUEST.md` exists, collect what it asks, delete it, rerun report-writer. After 3 loops the agent writes the report with verdict "could not decide" and the still-missing list up front. No question to the user at any point.
7. (user) Focus: every section after the first screen names the verdict line or decision-table row it supports, in its heading; a section that supports none is cut. Data collected but not bearing on the verdict goes under a collapsed "Also measured" appendix, one line each, number plus source. Shape and length follow the data and the question: no fixed word or section cap, but no paragraph over 3 lines at 390 px, no sentence that restates a number already visible in a table or chart beside it, and no "…" truncation.
8. (user) Every section that makes a claim has a picture (bar chart with spread bars, stacked time bar, timeline) or a table of the actual values next to its words; charts are built from `numbers.json` by a script in the output dir, so they can be regenerated.
9. (user) Modes: `desktop` writes one self-contained HTML page (inline SVG charts, opens in Firefox); `phone` writes 390 px wide PNG cards, each under 1,500 px tall, one per section, numbered. Both are rendered from the same source; the mode comes from the word phone/desktop in the prompt, else desktop (default). Plain-words meaning for every candidate or method name on first use (user, round 8).
10. (user) Fixture `agents/evals/report-writer/fixture/`: copies of the pogo files listed under Facts, the round-8 and round-9 PLAN/WORKER_NOTES, the two EVAL files, the round-8 phone cards and the round-9 HTML as "bad reports", and `question.txt` ("which GPU change, if any, should ship, and what is the next build"). Planted traps, each listed in `fixture/TRAPS.md`: a second file giving a different tail share for the same run; a crashed run (exit 1) with a numeric field present; a candidate with a single run and a large gain; a quantity named in the question that no file measures.
11. (user) Mechanical checks `agents/evals/report-writer/check.py` (run with `-I`): every number in the report (HTML text or the cards' source) exists in `numbers.json` and matches the fixture file it cites; each quantity has one value; every trap in TRAPS.md is flagged in "Wrong or missing" and no trap number appears as a plain figure; first-screen elements of R3 present; each section heading names a verdict line or row; no "…"; no paragraph over 3 lines; phone cards ≤1,500 px tall and 390 px wide. Exit 1 with the failing check named.
12. (user) `agents/evals/report-writer/RUBRIC.md`: the judgement criteria from this spec and the user's round-8/9 words, each with "pass looks like / fail looks like". `run.sh` builds the report from the fixture in both modes, runs check.py, opens the desktop HTML in Firefox (full Windows Firefox path per CLAUDE.local.md) and prints the card paths, so the user reviews; a `REVIEW.md` records each review round's verdicts, and the rubric and checks are extended from them. Criteria are provisional until the user has read a report (user).
13. (default) The report ends with a "How this was checked" line: numbers.json count, check.py result, what the agent could not verify.
