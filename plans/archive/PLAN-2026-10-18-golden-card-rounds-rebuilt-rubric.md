# Spec: Define a "good" report by golden-card rounds and a rebuilt rubric; render-only fixes; no report-writer run

## Ask
"I'm skipping the evaluator this round since I already know things aren't quite right. 1. Let's figure out what defines a 'good' report first before we do any more runs of the report-writer. We keep making one or two changes, then rerunning the expensive report-writer, and then repeating. Instead, we can collect all our fixes and apply them in one run at the end. 2. Review the recent worker notes and the recent evaluator sessions to get a starting point for what features I want in a 'good' report."
Round 1 — Card 1 purpose: "The first section should be the problem stated in my words-- a quote directly from me if possible." What's wrong: "None of these options seem right. I want you to research online for criterias for a good report, and also research how to make AIs write good reports. We may need to start from the ground up". Judging: "A golden card that the worker makes then presents to me; we iterate until its in a good spot. My ideal is that you show me options, get my feedback, and create a list of criteria over time of what goes into making a good report until we have things nailed down. To start, see if you can find some references reports online. I also like the idea of option 3 where we can compare old and new". Deliverable: "Option 3 [definition + render-only fixes]; once we have all the criteria figured out and I sign off, then I will go back to the planner and we will make the report writer then". Mid-round: "I don't like Amazon, exclude their ideas".
Round 2 — Problem quote: "Usually option 1 [the user's words from the planner session, PLAN.md `## Ask`], unless I asked for the report in the worker session, in which case the worker should say pass along the quoted ask". Principles: "A key factor that's extremely important is that the data and analysis in the report MUST be correct. Having every claim backed by evidence helps the AI not stray from the truth, but this tends to make the report very dense. Perhaps we first make the report in this dense fashion with every claim linking back to precise evidence, and then we make a second pass which focuses on concision and removes references to evidence that aren't as important so that we can make the report not so dense". Showing: "2-3 variants + old, phone PNGs in chat". Criteria list: "Rewrite RUBRIC.md from scratch".

## What to build
A definition of a good report, built with the user by eye, not by running the report-writer. The worker starts from the carried criteria below and the researched principles, hand-edits the existing `report.json`/`numbers.json` (fixture build #3 in `agents/evals/report-writer/out/`) into 2–3 golden-card variants of card 1 per round, renders them with `render.py` only, shows them next to the current card as 390 px PNGs in chat, records the user's pick and words, and grows a new `RUBRIC.md` from scratch, one confirmed row per thing the user judged. Render-side fixes (`render.py`, `cards.mjs`, `check.py`) that the user's picks demand are made now; `report-writer.md`, `report-checker.md` and `run.sh build` are not touched, and `claude --agent report-writer` is never invoked. The session ends when the user signs off the rubric; the next planner round turns it into the writer.

## Facts

Also why it's worth solving" (r3). Current card 1 (build #3) is 939 css px tall: problem → verdict → next action → deciding number → bars with axis break → reading → 5-row table → 6-item Wrong-or-missing.
- Verified (web, 2026-10-18, one search each): answer-first structure with 3–4 supporting points under the answer (Minto pyramid / BLUF, managementconsulted.com, betterup.com); decision memos separate observed evidence, assumptions and confidence and name the assumptions that would flip the decision (antoinebuteau.com; Duke Nicholas School memo guide adds counterarguments and reservations); ML reporting: report n per arm, mean and dispersion, never a single favorable run (koustuvsinha.com, arXiv 2504.07086, mlflow.org, n ≥ 3 as the common floor); LLM report grounding: prescribe the exact layout, feed only the data, verify claim by claim rather than an averaged score, small numeric deviations count as errors (arXiv 2604.27011, T2R-bench 2508.19813, AnalysisBank 2609.00818, Proof-Carrying Numbers 2509.06902, gmicloud.ai). AnalysisBank also runs a two-stage pipeline: one pass writes grounded analysis, a later pass imposes structure, which matches the user's dense-then-concise idea.
- Excluded by the user: Amazon six-pager/narrative-memo ideas.
- Unverified: no authoritative public one-page A/B or benchmark report template was found (Kohavi's book covers OEC and trustworthiness checks but no template; search results were course pages). The worker should treat "reference reports" as something to look for in a first round and show the user, not as settled.

## Requirements
1. (user) No run of `claude --agent report-writer` or `report-checker` in this round. All cards come from `render.py` on hand-edited copies of `out/*/report/report.json` and `numbers.json`. `run.sh build` and the two agent prompt files are unchanged.
2. (user) Card 1 opens with the problem in the user's own words: a verbatim quote from the study's `plans/PLAN.md` `## Ask` (the planner session), marked as a quote; when the report was asked for inside a worker session, the worker passes the quoted ask along instead. One sentence after it, in plain words, says why it is worth solving. Golden variants show this on the fixture using `fixture/plans/` text.
3. (user) Each round the worker shows, as 390 css px PNGs in chat: the current card 1 (old) and 2–3 hand-edited variants that differ in one named way each (e.g. what is on card 1 vs moved to card 2; chart treatment; table shape; caveat count and wording). Every variant is labelled with what differs. The user picks and corrects through the worker's questions; the worker never asks the user to design a card from nothing.
4. (user) Two-pass shape is one of the first things shown: a "dense" variant where every claim carries its evidence reference, and a "concise" variant of the same card where the less important references are removed and the prose is shortened, with the full references kept on a later card. The rubric records which references survive the second pass and which move down.
5. (user) `agents/evals/report-writer/RUBRIC.md` is rewritten from scratch. The old file moves to `agents/evals/report-writer/archive/RUBRIC-2026-10-18.md`. The new file has one row per criterion the user confirmed by eye: the criterion, the user's words that set it, the round and variant that proved it, and whether `check.py` can enforce it. Rows are added only after a user judgment; nothing is carried in on the worker's say-so.
6. (default) Candidate criteria the worker tests through variants, each from a source, none assumed: (a) carried from past verdicts: problem before verdict, verdict in words without figures, each figure once on card 1, chart with a written reading, honest axis start with break marks and note, n and spread beside every difference, not-run/not-measured/conflict/unproven named in a Wrong-or-missing box, write-readme voice; (b) researched: answer first with at most 3–4 supporting points, measured/assumed/unknown kept apart and the assumptions that would flip the verdict named, every figure traceable to file and field with a claim-by-claim check, dense pass then concise pass.
7. (user) The worker also looks for 2–3 reference reports online (a public one-page experiment, benchmark or A/B writeup) in its first round, shows them as links or screenshots, and asks the user which of their traits to keep; what the user names becomes candidate criteria. Nothing from Amazon's memo format is shown or recorded.
8. (default) The correctness criterion stays absolute: a golden variant may shorten, move or drop references, never change a value, n, spread or verdict; every figure on any variant is still a `numbers.json` reference, and `check.py` numbers/traps checks pass on every variant rendered.
9. (default) Render-side changes demanded by a user pick (block order, what moves to card 2, quote styling, table or caveat layout, chart marks) are made in `render.py`/`cards.mjs`/`check.py` as general rules, not fixture-specific, and the current build is rerendered from its unchanged `report.json` to show them.
10. (default) The rubric's rows are also recorded in `REVIEW.md` as a round with the user's words, and `plans/WORKER_NOTES.md` lists the fixes collected for the next planner round (prompt changes the writer will need) under one heading, so the next plan can apply them in one build.
11. (default) Each round ends with the worker asking whether the rubric is signed off; sign-off is the user saying so. On sign-off the worker writes the final rubric and stops; it does not build the writer.

## Constraints
Stack as the repo uses: bash, Python via uv (`render.py`, `check.py`), Node for `cards.mjs`, Markdown for the rubric. Phone PNGs sent in chat (the user reads on the phone, per EVAL_NOTES). No new services, no agent runs, nothing committed; the user commits.
